# Development constraints

- Keep the public site, `/admin`, content APIs and Better Auth in the root Nuxt app. Install `@liria24/site-admin` as a package: verify with `bun link`, then a commit-specific pkg.pr.new URL. Stable SDK releases use its existing uppt workflow.
- Void owns D1/R2 connections, local emulation, migrations and Cloudflare deployment. Keep resource configuration in `void.config.ts`, generated schema in `db/schema.ts`, and reviewed SQL in `db/migrations`. Do not reintroduce application database factories, SDK adapters or generated Wrangler configuration patches. Use `db` from `void/db` for application-specific queries.
- `APP_ENV=production` selects `liry24-com`, the existing production D1/R2, the custom domain and its minute Cron. The default/dev target is `liry24-com-dev` with separate D1/R2, no production routes and no Cron. Only `dev` deploys through the Preview GitHub Environment. Do not create branch cleanup jobs or copy production data into dev.
- Commit Void's resolved lockfile after provisioning; verify the resource names/IDs before selecting another environment. Production migration/deployment requires a separate explicit instruction. Ordinary builds and HTTP requests never apply DDL or rebuild indexes; Void applies reviewed SQL during development startup and an explicitly requested deploy.
- A new baseline cannot be applied blindly to an existing database. Back up the source, apply the legacy model/history/i18n transformations on a copy, validate all rows and foreign keys against the new schema, rebuild search, then align the Void/D1 ledgers. Retain the old `drizzle/` inputs until this transition is verified on the actual exported database. Do not modify old `.data/unified` data. Keep temporary migration tools, exports and operational evidence outside tracked source; do not add migration README/docs.
- Use Vitest. D1/workerd/R2 tests use synthetic bindings with no remote access. Their persistence must be separate from development data. Local development is Void's local D1/R2; no application SQLite driver or migrator may enter Worker bundles.
- Keep published, scheduled and current revisions separate. `socials` and `ranks` disable scheduling and history. This app disables draft Blob separation, so unpublished originals remain accessible to anyone who knows their public R2 URL.
- Preserve Better Auth patches that bound rate-limit counters by the actual router's registered template and one unknown-path bucket. Retain route-specific limits; rebase or retire patches when updating packages.
- Authentication secrets and OAuth apps are separate for production and dev. Use direct `/api/auth/callback/<provider>` URLs without an OAuth proxy. Runtime secrets live in Void/Cloudflare bindings, never build output. OG Image requires a separate `NUXT_APP_SECRET` of at least 32 characters for each environment.
- Deployed dev login requires the GitHub identity to have current `admin` permission on `Liry24/liry24.com`. Recheck at management APIs and fail closed on lookup errors. Local Nuxt development does not call the Preview permission service. Only deploy trusted dev code because deployment uses secrets.
- GitHub Environment `Preview` holds the Cloudflare token, dev auth/OG signing secrets, OAuth credentials and repository permission lookup token. Cloudflare and permission lookup tokens expire on 2026-12-30; replace them before expiry. Never log secret values.
- Renovate uses `renovate/`, targets `dev`, and runs only secretless quality checks. The default `main` needs `renovate.json` with `useBaseBranchConfig: merge` before enabling its App. Do not change Cloudflare Workers Builds settings in this task.
- Publication slug policy and proofreading review belong to the app. Keep `ai.actions`, preparation hooks and the posts field definitions aligned; generic upload/save/publish state belongs to Site Admin.

- Keep the Void 1.1.11 native-WASM patch until upstream preserves Worker WASM modules when rebundling Nuxt output; the built Worker integration test exercises that exact deployment path.
